# Build 32 firmware — code provenance map

**Purpose:** know which functions are proprietary **RED** code (must be lifted to
C/C++) versus **third-party** code (VxWorks, OpenSSL, Xilinx — keep as inlined
assembly / blob). This scopes the decompilation: we only rewrite RED code.

Generated by `firmware/scripts/build_provenance_map.py` →
`src/manifest.json` + `src/manifest.csv` (one row per function).

## The four provenances (and how we identify them)

The image is a stripped, fully-linked flat binary (file offset == runtime address,
load base `0x0`) — **no symbol table, GOT/TOC, or SDA base**. But the toolchain left
**embedded source-path strings** (`__FILE__`), which cleanly identify each origin:

| Provenance | Marker (embedded path / strings) | Files seen | Treatment |
|---|---|---|---|
| **vxworks** | `C:/WindRiver2.6/vxworks-6.4/...` + the WIND kernel | `edrStub.c`, `usrMmuInit.c` (+ symbol-less kernel) | keep as blob |
| **openssl** | OpenSSL 0.9.8a / "Wind River Security Libraries": `a_*.c`, `bn_*_cci.c`, `v3_*.c`, `conf_*.c`, `evp_*.c`, `x509*`, ASN.1 | ~80 source files; code block ≈ `0x380000–0x384800` | keep as blob |
| **xilinx** | `C:/sundance/.../ppc405_0_drv_csp/xsrc/x*.c`; sources mirrored at `~/src/RED/drivers/` | **43** driver files | keep as blob (identify/verify only) |
| **red** ← target | `apps/Sundance/`, `app_modules/*`, `lib/*`, `drivers/*` | **76** source files | **lift to C/C++** |

File-level composition is therefore **fully known**. The RED application tree:
`apps/Sundance/` + 56 `app_modules/*` (digmag, upgrade, master, parammgr, videomgr,
vpimgproc, ui_engine, ui_ip, ui_usb, imageanalysis, calibrate, …) + 11 `lib/*`
(libsensor, libpipeline, libstorage, libcodec, libvpcomm, …) + 5 `drivers/*`
(fpgaloader, hdmi, frametimer, …).

## Per-function attribution is a *seed* map, not exhaustive

Mapping each of the 10,554 stripped functions to a source file is a hard problem:
string signals only reach functions that reference a distinctive string, and Ghidra
left ~all functions named `FUN_xxxxxxxx`. The manifest is therefore **confidence-tiered
and honest** — what it can't pin down it labels `unknown` rather than guessing:

| method | conf | meaning |
|---|---|---|
| `source-path` | 3 | function materializes a `__FILE__` source-path string → ground truth |
| `region-openssl` | 3 | inside the OpenSSL/WR-Security code block |
| `named-symbol` | 3 | Ghidra-named libc/VxWorks routine (memset, strncmp, …) |
| `string-flavor` | 2 | dominant flavor of all strings the function references |
| `callgraph` | 2 | provenance shared by ~all callers (low-fan-in only) |
| `region` | 1 | coarse address-range fallback (kernel / BSP tail) |
| `unknown` | 0 | not yet attributable — triage/reconstruction candidate |

Current coverage: ~280 functions at conf ≥ 2 (93 RED w/ module labels, 86 OpenSSL,
385 VxWorks); the rest `unknown`. **This grows monotonically as we reconstruct:**
each reconstructed module pins its functions, and their call-graph closure inherits
the label — so the `unknown` bucket shrinks module by module.

## How to use it

```bash
python3 firmware/scripts/build_provenance_map.py          # regenerate manifest

# RED functions confidently attributed to a module (reconstruction targets):
awk -F, '$5=="red" && $8>=2' firmware/reverse/build_32/src/manifest.csv

# everything attributed to one module:
awk -F, '$6=="app_modules/digmag"' firmware/reverse/build_32/src/manifest.csv
```

## Improving coverage (future work)
The strongest unused signal is **Ghidra's own resolved xrefs** (it follows the
base+displacement string references this pure-binary scanner misses). A headless
Ghidra xref/call-graph export (extending `firmware/scripts/ghidra_*.py`) would
attribute far more `.cpp` app-module functions. Until then, coverage is driven by
the `source-path`/`string-flavor` seeds plus reconstruction.
